入力と検索適用値を分けて保持。NFKC正規化、日本語ロケール小文字化、連続空白の圧縮後、単語ごとのAND部分一致で検索。本文・理由・日時・ポイント等も対象。種別別にナレッジ、スキル、実績の順で結合し、全種横断の日付ソートは行わない。状態指定がある場合、スキルと実績は除外。

4. 登録・削除処理

4.1 ナレッジ登録

  1. 対象・本文・機密確認を検証。不足時は処理終了。
  2. フォームからリスク値とカテゴリを推定。変更されていないAI評価があればhidden入力から取得。
  3. POST /api/knowledgeで新規作成。APIは評価指定を優先し、未指定時はルール計算。
  4. 成功時は3種のGETで状態を再読込。
  5. フォーム・任意詳細・会話を初期化し、登録画面を表示。

既存ナレッジの展開後もPOSTで新規作成する。更新APIはない。またHTTPエラーでもフォーム初期化へ進む。通信例外のcatchは登録関数にない。

4.2 スキル・実績

本文をtrimし、空なら終了。title・yearMonth・任意aiEvaluationをPOST。成功時は状態を再取得。年月はAPIで月初00:00 UTCへ変換し、未指定時は現在日時を使用。

4.3 削除

window.confirmで確認 → 種別APIへDELETE?id=… → 成功なら状態再取得。HTTPエラー時はalertを表示。ナレッジはdeletedAt更新の論理削除、スキル・実績はdeleteManyの物理削除。いずれもデモユーザーIDを条件に含める。

5.1 ナレッジPOSTの補足

workContext・descriptionはtrim後必須。occurredAt未指定は現在時刻。actualHarmはminor/occurred以外をnoneへ、statusはcompleted以外をconsideringへ変換。categoriesは配列のみ受け付け、偽値除外・文字列化・先頭5件。occurrence/severity/detectabilityはNumber変換、各既定3。rpn既定27。riskLevelは4列挙値以外low。summaryは「{subject}で得た気づきを記録しました。」。

6. 評価・集計ロジック

6.1 登録値の決定順

有効なaiEvaluation → 登録API固有のルール。aiEvaluationはpointsをNumber変換して有限数か確認し、0～100へ制限して四捨五入。reasonは文字列化・trim後必須。API側で外部AIへ再照会しない。

AIプレビューはtitle/content/extraContextのJSONを比較し、評価後に入力が変われば古い結果と表示する。古い結果のhidden入力は除去され、登録APIのルール計算へ戻る。

6.2 KP（登録APIの未評価時）

条件点数
基本点10
descriptionが30文字以上+10
detectionTriggerが空でない+10
perceivedCauseが空でない+10
対象・本文・任意4項目に「チェック|レビュー|自動|検証|監視|手順|防止」のいずれか+10
riskLevelがhighまたはcritical+10

上限60KP。AIプレビューのfallbackEvaluation(knowledge)は別ルール：基本10、trim後content30文字以上、発見関連語、原因対策関連語、高リスク関連語で各+10。現行条件では最大50。リスクは40点以上high、25点以上medium、それ以外low。criticalは返さない。したがってプレビュー評価の有無で登録点数が変わり得る。

6.3 SP / AP

小文字化した入力を上位行から判定し、最初に一致する値を使用。登録APIはtitleを判定し、AIフォールバックはtitleとcontentを連結して判定。

6.4 リスク・カテゴリ

occurrence = 工夫に「注意」を含む ? 4 : 3
severity = 影響あり(occurred) ? 5 : 想定影響あり ? 4 : 3
detectability = 発見契機あり ? 3 : 4
RPN = occurrence × severity × detectability
RPN >= 80 : critical / >= 50 : high / >= 20 : medium / その他 : low

現在の推定値の最大積は80。カテゴリは13候補から対象・本文・原因・工夫の語句一致で推定し、レビュー・確認/照合の補助判定を追加、重複除去して最大3件。該当なしは「その他」。

6.5 EP・レベル・グラフ

再読込後のtotalXp = Σ knowledgePoints + Σ skill.points + Σ achievement.points
level = floor(sqrt(totalXp / 100)) + 1
今月の成長 = 今月KP + 今月SP + 今月AP + 今月の付与済みquest.xp

totalXpは画面上EPとして扱う。今月判定は端末ローカルの年・月。登録数グラフは発生日時順に1ずつ累積。EPグラフは付与済みクエストと3種の登録を日付順で累積し、開始値はmax(0, 総EP−イベント合計)。SVGは720×220の座標系、余白34、Y軸上限の最低値100。

6.6 外部AI

キー設定時は https://openrouter.ai/api/v1/chat/completions へPOST。Bearer認証、HTTP-Referer、X-Titleを付与。systemでJSON、0～100の整数点、4値リスク、日本語理由を指示。userにkind/title/content/extraContextをJSON化し、response_format=json_objectを指定。

choices[0].message.contentをJSON解析。pointsがnumberなら0～100へ制限し、理由欠落時は既定文。実装では整数丸め・riskLevelの厳密検証は行わない。非2xx、解析例外、points欠落はルールへ戻す。明示的なタイムアウト・再試行はない。

7. 月次レポート

  1. yearMonthを分解し、UTCの当月1日00:00をstart、翌月1日00:00をendとする。
  2. occurredAt / acquiredAt / achievedAtが[start,end)の3種レコードとUserを並列取得。
  3. 件数とKP/SP/APを合算しmonthlyGrowthを算出。総EPはUser.totalEpを取得。
  4. 0件時または登録ありの場合の定型月次文、総EP・成長を埋め込んだ定型エンジニア評価を生成。
  5. userId+periodKeyでupsertし、再生成時は期間・生成時刻・評価・snapshotJsonを上書き。

snapshotJsonはknowledgeCount、skillCount、achievementCount、knowledgePoints、skillPoints、achievementPoints、totalEp、monthlyGrowthの9値。periodEndは翌月開始の排他的境界。外部AIは使用しない。

画面は成功応答を同年月の既存レポートと入れ替える。HTTP非成功時はbuildAiReportのローカル版を作り保存する。通信自体がrejectした場合のcatchはない。getSavedReportsは旧latestReportも統合し、年月を正規化して同月重複を解消する。

レポート集計にはdeletedAt=null条件がなく、論理削除済みナレッジも含む。登録APIはUser.totalEpを更新しないため、画面の総EPとレポートの総EPが一致しない可能性がある。

8.1 全フィールド定義

以下は作成時のPrismaスキーマから収録。?は任意、[]は配列、@defaultは既定値。StringのDB型未指定はPostgreSQLのtextに対応する。

User

model User {
  id                 String              @id @default(uuid()) @db.Uuid
  email              String              @unique @db.VarChar(320)
  displayName        String              @db.VarChar(100)
  timezone           String              @default("Asia/Tokyo") @db.VarChar(64)
  monthlyReportDay   Int                 @default(1) @db.SmallInt
  monthlyReportTime  DateTime            @default(dbgenerated("'07:00:00'::time")) @db.Time(0)
  totalEp            Int                 @default(0)
  createdAt          DateTime            @default(now()) @db.Timestamptz(3)
  updatedAt          DateTime            @updatedAt @db.Timestamptz(3)
  knowledgeEntries   KnowledgeEntry[]
  acquiredSkills     AcquiredSkill[]
  achievementRecords AchievementRecord[]
  monthlyReports     MonthlyReport[]
  pointEvents        PointEvent[]

  @@map("users")
}

DB例外・不正JSON等Route Handler共通の捕捉・エラー形式は未定義。正常系JSONと同じ形式の保証はない。

現行は固定デモユーザーのため実ユーザー認証・所有者分離を提供しない。aiEvaluationはクライアント指定値を採用するため、評価結果のサーバー検証や署名はない。機密確認は画面側のみで、API直接呼び出しでは検証されない。

maskSecretsは秘密鍵・Bearerトークン・key/token/password/secretの代入表現を置換するが、整理メモの補助データに限定される。元の相談文も保持・表示され、AI評価APIへ送る入力やDB保存データを一律にマスキングする処理ではない。

11. 実装上の制約・確認観点

以下は現状の記録であり、本書作成に伴うコード修正は行っていない。

論点現状と確認すべき動作
EPの整合画面は3種データを再集計、今月成長・グラフは旧クエストも加算。レポートは更新されていないUser.totalEpを参照。既存クエストありの表示差を確認。
論理削除一覧GETでは除外、月次集計では未除外。削除後の再生成結果を確認。
既存レコード再登録一覧から開いて登録すると新規作成。更新と誤認しない画面運用が必要。
年月とタイムゾーンレポートAPIはUTC境界、ダッシュボードは端末ローカル月、生成月はUTC。datetime-local送信値にオフセットがなくサーバー依存。月末・月初を確認。
レポート永続性DBに保存するが起動時の履歴取得なし。ブラウザー初期化後にDB履歴は画面復元されない。
入力検証年月書式、日付妥当性、数値の範囲、本文長、kindの列挙検証がAPIで不十分。リスク積の再計算も行わない。
登録失敗・多重送信保存エラー時の案内・フォーム維持や送信ロックが不足。PointEventの冪等キーは現行登録処理で利用しない。
AI評価差未評価、最新プレビュー、入力変更後、外部AI失敗の各経路で点数・理由・リスクを確認。
運用機能通知設定は読取表示のみ。自動通知ジョブ・実認証・ポイント台帳更新は未実装。

最低限のレビュー例：必須項目400、削除対象なし404、削除成功204、同年月upsert、検索の全半角・複数語AND、状態指定時の種別除外、AI未設定時のフォールバック、ストレージ消去後のDB再読込。本書では確認観点を列挙しており、実行済み試験を意味しない。
